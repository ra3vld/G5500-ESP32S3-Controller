# Классический ESP32 WROOM/WROVER

Профиль `BOARD_ESP32` рассчитан на обычные ESP32 DevKit, DevKitC и NodeMCU с Flash от 4 MB и доступными GPIO из таблицы. Общая распиновка подходит модулям WROOM и WROVER: GPIO6…11 и GPIO16/17 не используются, PSRAM не требуется. Платы со встроенными экранами, SD-картой или другой периферией нужно сверять отдельно. [Ограничения DevKitC и WROVER у Espressif](https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32/esp32-devkitc/user_guide.html).

## Подключение

| Назначение | GPIO |
|---|---|
| ADC обратной связи AZ / EL | 34 / 35 |
| AZ отрицательное / положительное, LEFT / RIGHT | 25 / 26 |
| EL отрицательное / положительное, DOWN / UP | 14 / 27 |
| AZ / EL скорость либо ENABLE | 32 / 33 |
| USB-UART0 RX / TX | 3 / 1 |
| Внешний HC-05: RX ESP32 / TX ESP32 / STATE | 39 / 5 / 15 |
| Подтверждение ожидающей цели | 0, кнопка BOOT |
| TFT MOSI / SCK / MISO | 23 / 18 / 19 |
| TFT CS / DC / RST | 21 / 22 / 4 |
| XPT2046 CS / IRQ | 13 / 36 |
| LCD1602 RS / E | 21 / 22 |
| LCD1602 D4 / D5 / D6 / D7 | 23 / 18 / 19 / 4 |

TFT и параллельный LCD1602 — альтернативные сборки; LCD RW соединяется с GND. Для LCD с логикой 5 В сохраняется требование согласования уровней. Светодиодная индикация по умолчанию отключена, поскольку её GPIO различаются между платами. GPIO34…39 — только входы, без внутренних подтяжек. Обратная связь использует ADC1 и работает одновременно с Wi-Fi; на входы нужны делитель и защита согласно [аппаратной документации](hardware.md).

YAESU, SEPARATE_PWM и BTS7960 сохраняют свои назначения сигналов и правила подключения. Схемы S3 показывают другую нумерацию GPIO: переносите соединения по названиям сигналов, используя эту таблицу. В YAESU GPIO33 не используется; в G-800DXA выходы EL остаются выключенными.

## Bluetooth и USB

При `BLUETOOTH_ENABLED=1` и `BLUETOOTH_MODE=BT_AUTO` (или `BT_ESP32_SPP`) ESP32 запускает встроенный Bluetooth Classic SPP с именем **G5500-Rotator**. BLE отключён. На ПК или Android выполнить обычное сопряжение; ввод PIN или подтверждение на контроллере не нужны. Транспорт использует [асинхронный SPP API ESP-IDF](https://docs.espressif.com/projects/esp-idf/en/v5.5.5/esp32/api-reference/bluetooth/esp_spp.html) без дополнительной задачи и очередей `BluetoothSerial`; скорость виртуального COM-порта не задаёт скорость радиолинка. На S2/S3 этот профиль не применим: там сохраняется внешний HC-05.

Для внешнего модуля задайте `BLUETOOTH_ENABLED=1` и `BLUETOOTH_MODE=BT_HC05` в `build_config.hpp`. В этой сборке встроенный SPP не запускается. HC-05 использует отдельный UART1, 9600 бод, 8N1: **TXD модуля → GPIO39**, **RXD модуля ← GPIO5**, **STATE → GPIO15**, общий GND. Логические сигналы должны иметь уровень 3,3 В; питание VCC выбирайте по конкретной плате модуля. GPIO не пересекаются с приводом, UART0, TFT/touch или LCD1602 и не занимают GPIO16/17 WROVER.

GPIO5 и GPIO15 — strapping-выводы. LOW на STATE/GPIO15 при сбросе подавляет ROM-загрузочный текст UART0; GPIO5/15 также задают тайминги неиспользуемого SDIO slave. Назначения приведены в [даташите Espressif, Boot Configurations](https://documentation.espressif.com/esp32_datasheet_en.html). Состояние соединения HC-05 читается с STATE; MAC модуля через обычный UART неизвестен и в вебе не показывается.

```sh
python3 tools/build_platformio.py --env esp32_4mb --bluetooth 1 --bluetooth-mode hc05
```

SPP принимает тот же GS-232, что USB-UART0, включая запросы положения, STOP, направления, цели и калибровку. Числовые внешние цели в ручном режиме ожидают подтверждения. Разделители CR/LF/CRLF, максимум 512 байт на строку; повреждённая или слишком длинная строка отбрасывается до разделителя. Входная очередь вмещает до восьми полных строк и суммарно до 1024 байт. Очередь ответов — до восьми ответов и суммарно до 512 байт, отдельно от уже переданного драйверу ответа. Буферы статические: callback SPP не наращивает строки и контейнеры. Перегрузка отбрасывает целые команды/ответы с записью в журнал, обработка управления продолжается. При разрыве SPP незавершённый ввод, ранее принятые команды и ожидающие ответы не переносятся в новое соединение.

Веб показывает выбранный транспорт (SPP или HC-05) и фактическое подключение клиента. API сохраняет `build.bluetooth` и `btConnected`, добавляет неизменяемое поле `build.bluetoothBackend`: `ESP32_SPP`, `HC05` или `NONE`. При отключённом Bluetooth его объект и библиотека исключаются при сборке через `build_platformio.py`.

В карточке «Подключение» показан **Bluetooth MAC** контроллера — его нужно ввести в поле MAC в Look4Sat. Адрес можно выделить целиком. «Bluetooth-соединение» показывает фактическую связь с телефоном, даже когда канал приложения ещё не открыт или команды не поступают. «Канал SPP» показывает открытый последовательный канал; передавать данные для появления `CONNECTED` не нужно. Сопряжение, сохранённое в настройках Android, само по себе не является активным соединением. В `/api/status` добавлены `btMac` и `btLinkConnected`; `btConnected` сохраняет значение состояния SPP. При HC-05 адрес внешнего модуля через обычный UART неизвестен, поэтому отдельная строка MAC скрыта.

USB-мост платы использует GPIO3/1: GS-232 на 9600 baud и загрузка прошивки. Диагностика приложения остаётся в веб-журнале `/diaglog`. ROM при сбросе может выдавать загрузочный текст на 115200 baud; это не поток диагностики приложения. Ошибка запуска SPP записывается в журнал, USB и сетевое управление продолжают работать.

На классическом ESP32 журнал занимает фиксированные 2048 байт и сохраняет последние полные строки, чтобы работа Wi-Fi/SPP не исчерпывала heap растущими строками. S2/S3 сохраняют журнал на 160 строк. Если веб недоступен, отправьте `H4` с окончанием CR/LF через монитор порта на 9600 бод: ответ покажет свободную heap, минимум, наибольший блок, расходы этапов запуска и состояние Wi-Fi/NVS без пароля. Дополнительная строка `PSRAM available=yes total=… free=… min=… max=…` показывает общий размер внешней heap, свободный остаток, его минимум с момента запуска и наибольший свободный блок в байтах. При недоступной PSRAM выводятся `available=no` и нули; это может означать как отсутствие памяти, так и отключение в сборке или ошибку инициализации. Значение `WIFI status=3` означает подключение STA к роутеру; `savedSSID=yes` означает наличие загруженного SSID. Снятые на старте `beforeBT`, `afterBT`, `afterAP`, `afterWiFi`, `setup` и текущие `free`/`max` позволяют отличить расход запуска от последующего роста потребления.

При встроенном SPP Wi-Fi запускается с ограниченными очередями: 2 постоянных RX-буфера, 4 динамических RX и 2 TX вместо стандартных 32/32, 2 служебных RX-буфера и 8 коротких служебных буферов; агрегация AMPDU/AMSDU отключена. Это уменьшает расход RAM ценой максимальной пропускной способности. По умолчанию (`ESP32_FORCE_AP_STA=0`) при доступном роутере работает только STA, Bluetooth остаётся включённым. AP запускается как резерв при отсутствии соединения; во время повторной попытки STA временно работает AP+STA. Политика и сроки описаны в [подключении Wi-Fi](usage.md#подключение-wi-fi). Переход в AP после неудачного подключения не переинициализирует драйвер. В ответе `H4` поле `profile=compact` подтверждает успешную инициализацию этого профиля; `standard` означает обычную конфигурацию или отказ компактной инициализации. Фактический запас памяти и устойчивость радио нужно измерить на плате.

UDP-порты N1MM и PstRotator работают через сокеты без постоянных передающих буферов `NetworkUDP`: убраны два выделения по 1460 байт. Приём выделяет один ограниченный буфер только на время обработки пакета; XML-парсер читает его через `string_view`, без копий исходного текста. Пакеты больше 4096 байт отбрасываются целиком. Если буфер выделить не удалось, пакет пропускается, очередь продолжает обслуживаться. Порты команд, ответов и отчётов положения сохраняются.

В первой строке `H4` поле `elf=` содержит первые 12 символов SHA-256 ELF загруженной прошивки. Оно позволяет сопоставить замер с конкретной сборкой. Если отсутствуют `elf=` или поля `cause/errno/bytes` в строке HTTP, на устройстве ещё более ранняя сборка; один и тот же `profile=compact` версию не определяет.

Частый опрос `/api/status` по HTTP/1.1 использует одно TCP-соединение повторно. Это уменьшает накопление закрытых соединений в `TIME_WAIT` (в поставляемой конфигурации lwIP они могут сохраняться до 120 секунд). После 1500 мс без нового запроса соединение закрывается; ожидающий второй клиент получает доступ раньше этого срока. Остальные маршруты, HTTP/1.0, явный `Connection: close` и конвейер запросов сохраняют закрытие после ответа. Заголовки ответа освобождаются сразу после отправки. Дробные числа JSON форматируются через `std::to_chars` в фиксированный буфер, без сохраняемых рабочих выделений newlib `printf`.

В `H4` счётчик `requests` означает обработанные HTTP-запросы, а `accepted` — принятые TCP-соединения: при обычном опросе одной открытой страницы первый должен расти заметно быстрее второго. `BTlink` показывает наличие Bluetooth ACL-соединения даже без открытого SPP. Отдельная строка `TCP` показывает активные соединения, число закрывающихся среди них, `timewait` и размер базовой структуры `pcbBytes` без накладных расходов аллокатора. Снимок читается под блокировкой ядра lwIP; если сборка не поддерживает эту блокировку или сеть ещё не инициализирована, выводится `stats=unavailable`. Те же счётчики TCP и HTTP доступны в `/api/status`. Эти данные помогают отличить удержание TCP-структур от других расходов и фрагментации; сами по себе они не доказывают отсутствие утечки.

Для передачи HTML допускается пауза без прогресса до 10 секунд и общее время до 30 секунд. Прежняя пауза в 2 секунды была короче начального TCP RTO в 3 секунды и могла оборвать страницу раньше повторной передачи потерянных пакетов. JSON-статус сохраняет ограничения 2 секунды без прогресса и 15 секунд всего. Ожидание выполняется между итерациями основного цикла; USB, Bluetooth и управление осями продолжают обслуживаться. Поля `cause/errno/bytes` сохраняют последнюю ошибку даже после успешных ответов, поэтому при повторной проверке сравнивайте также изменение `txFailures`.

Веб-страницы заранее сжаты gzip и хранятся во flash; ESP32 не запускает компрессор и не держит распакованную страницу в heap. Главная страница передаётся как 10 786 байт вместо 35 852. Клиенты без поддержки gzip получают исходный HTML. Страницы и статус отправляются порциями с паузой не менее 20 мс, чтобы не заполнять сразу все очереди передачи. Временные `ENOMEM`/`ENOBUFS` допускают повторную попытку в пределах общего срока отправки.

После изменения HTML запустите `python3 tools/generate_web_assets.py`. Заготовки включены в исходники для Arduino IDE; контрольная сумма при компиляции обнаруживает рассинхронизацию HTML и gzip. `tools/build_native.sh` и `tools/prepare_sketch.py` также проверяют актуальность и целостность сжатых данных.

Для принудительного сохранения AP вместе со STA установите в `build_config.hpp`:

```cpp
#define ESP32_FORCE_AP_STA 1
```

Либо передайте `-DESP32_FORCE_AP_STA=1`. **Это повышает расход RAM и может вызывать зависания, перезагрузки и отказы Wi-Fi/веба, особенно вместе со встроенным SPP.** При запуске предупреждение записывается в журнал. Значение по умолчанию — `0`, резервная AP. На S2/S3 AP включена постоянно независимо от этого флага. В `H4` поле `apPolicy=always` подтверждает постоянную AP, `fallback` — резервную; `runtimeMode` показывает фактический режим в момент замера.

## Ограничение пиков RAM

Оптимизация не требует пересборки ESP-IDF/Arduino SDK. Wi-Fi, веб и встроенный SPP работают одновременно; по умолчанию AP используется как резерв. XML разбирается через представления исходного пакета и ограниченный пул узлов на стеке; командные последовательности используют массивы до 16 целей. Разбор чисел не вызывает `strtof` или потоков C++. Транспорт UDP по-прежнему временно выделяет буфер до 4097 байт: устранение выделений внутри парсера не означает отсутствие выделений в сетевом стеке.

HTTP до штатного парсера проверяет пределы: 4096 байт всего, 512 байт первой строки, 32 заголовка до 1024 байт каждый, суммарно 32 параметра query/body; после URL-декодирования ключ до 32 байт и значение до 128 байт. Неверные escape-последовательности и управляющие байты отклоняются. Для обычных обработчиков запас heap учитывает размер запроса, поскольку штатный POST-парсер держит несколько копий формы. Параметры передаются API через `string_view`, а выделенные штатным парсером строки освобождаются сразу после обработчика.

Точные GET-запросы `/api/move?d=S`, `?d=A`, `?d=E` после проверки полного HTTP-запроса останавливают соответствующие выходы до heap-проверки и штатного парсера. Это сохраняет STOP при нехватке памяти для обычного API. Приём TCP всё равно требует памяти; если единственный HTTP-слот занят передачей страницы, новый запрос ждёт освобождения слота. Это не аппаратная аварийная кнопка.

Журнал, все интервалы RSSI и история сбросов отправляются через общий буфер ответа без растущей строки всего документа. UART/TCP обслуживают до 128 входных байт и четырёх команд за проход; SPP — до четырёх команд. Приём проверяет бюджет 2 мс между командами, UDP — между пакетами. Обычная отправка HTTP и TCP ограничена бюджетом 5 мс. Это не жёсткое ограничение времени всей итерации: отдельный обработчик или NVS может занять больше. `H4` теперь отправляется построчно из буфера 256 байт: UART получает только доступное для записи число байт, SPP повторяет попытку при заполненной очереди. Общий срок ответа — 5 секунд; повторный `H4` во время ответа не начинает его заново и не меняет транспорт. Поля снимаются при формировании очередной строки, поэтому весь ответ не является одномоментным снимком.

Строка `RUNTIME` в `H4` содержит:

- `allocHook=OK`, `allocFailures`, `maxFailed`: регистрация счётчика отказов распределителя, число отказов и максимальный запрошенный размер в байтах. Callback обновляет атомарные счётчики и сохраняет первые отказы в двух группах: запросы меньше 1024 байт и от 1024 байт. Печати и выделений памяти внутри callback нет. Это не трассировка утечек.
- `loopMaxUs`, `loopsOver20ms`: максимум времени работы основного цикла в микросекундах и число проходов дольше 20 мс, без заключительной паузы 5 мс. В старых сборках синхронный вывод `H4` по UART сам увеличивал этот максимум примерно на время передачи ответа; теперь передача распределена между проходами цикла.
- `stackMin`: минимальный свободный остаток стека задачи основного цикла в байтах с момента её запуска.
- `btRxDropped`: число полных входных команд, отброшенных при переполнении очереди SPP.

Если зарегистрирован отказ выделения, `H4` добавляет до двух строк `OOM`: запрошенный `size`, маску требований `caps` в hex, свободную внутреннюю byte-accessible память `free/max`, имя задачи `task`, функцию распределителя `fn` и адреса `pc` стека вызовов. Первый опубликованный образец в каждой группе сохраняется до перезагрузки и не перезаписывается поздними ошибками. `fn` обычно называет распределитель, а вызывающий код определяется по `pc`; маска `caps` важна, поскольку не все свободные блоки подходят каждому запросу. На Xtensa сохраняется до восьми адресов; нули в конце означают конец доступного стека. Адреса расшифровываются **только ELF этой сборки**, соответствующим `elf=`:

```sh
xtensa-esp-elf-addr2line -pfiaC -e G5500_Fork.ino.elf 0x400xxxxx 0x400yyyyy
```

Отключение AP не освобождает все структуры её интерфейса: штатный Arduino-core создаёт STA и AP netif при инициализации Wi-Fi. STA-only уменьшает расходы работающей AP, но величину экономии и устранение отказов нужно измерить на устройстве. Изменения не требуют отдельного SDK.

Счётчики отказов выделения и длительности цикла также доступны в `/api/status`. Для проверки на плате сравните `H4` после загрузки, подключения SPP, работы одной веб-страницы 10–15 минут и через 2–3 минуты после её закрытия. Следите за динамикой `free/max`, `allocFailures`, `HTTP requests/accepted/txFailures` и `TCP timewait`; единичное значение минимума heap само по себе не доказывает продолжающуюся утечку.

## Сборка

```sh
pio run -e esp32_4mb
pio run -e esp32_4mb_lcd
pio run -e esp32_4mb_tft
python3 tools/build_platformio.py --env esp32_4mb --display tft --bluetooth 0 --drive bts7960
./tools/build_arduino.sh esp32
```

Для Arduino IDE откройте исходный `G5500_Fork/G5500_Fork.ino`, выберите ESP32 Dev Module, Flash 4 MB, DIO 40 MHz, PSRAM Disabled, Core Debug Level None и Partition Scheme **Huge APP (3MB No OTA/1MB SPIFFS)**. `BOARD_PROFILE=BOARD_AUTO` можно оставить. В исходной папке нет `partitions.csv`, поэтому IDE генерирует таблицу из выбранной схемы; отдельная копия не требуется. В старых копиях скетча удалите `partitions.csv`, если хотите использовать меню.

PlatformIO и сборочные скрипты используют `partitions_esp32.csv`: один factory-раздел приложения 3 MB, поскольку Wi-Fi + SPP превышают старый слот 1,97 MB. Второго OTA-слота нет; веб-OTA в текущей прошивке отсутствует. NVS остаётся на `0x9000`, разметки S2/S3 сохранены. `prepare_sketch.py --target esp32` остаётся доступен для отдельной копии с явно заданной разметкой проекта.

Сборки и тесты с имитацией Bluetooth проверяют код и границы транспорта. Сопряжение, совместная работа радио Wi-Fi/SPP, свободная runtime heap, дисплей, датчики и двигатель требуют проверки на конкретном устройстве.
