Используйте [порты](../setup/network.md#порты) своего устройства. HTTP и команды управления доступны в локальной сети без отдельной авторизации. `token`, `generation`, `boot`, `selection` и `rangeRevision` защищают от устаревших запросов; они не заменяют пароль доступа к сети.

HTTP-формы передаются как `application/x-www-form-urlencoded`. [OTA](../maintenance/ota.md#http-api) имеет отдельные заголовки и бинарную загрузку. Командный транспорт использует те же пути и поля, но все изменения выполняет через POST; HTTP сохраняет некоторые старые GET-операции. При потере ответа сначала нужно прочитать состояние потому что команда могла выполниться без подтверждения. Для HUD дождитесь результата `requestId`; подтверждение команды не означает достижения цели.

Страница оборудования и HTML-страницы ESP32-S2, ESP32-C3 и ESP32-3248S035C используют `Content-Encoding: gzip`. Браузер распаковывает их автоматически; при загрузке HTML через curl добавьте `--compressed`.

## HTTP API управления

Операции POST принимают `application/x-www-form-urlencoded`:

| Метод / путь | Поля |
|---|---|
| GET `/api/status` | model, controlMode, remainingMs, pendingValid/pending, presetActive/presetSlot, presets, speedEnabled/speedPercent, startSpeedPercent, approachSpeedPercent, accelerationMs, decelerationMs, slowdownDegrees, coastDegrees, decelerationFactor, speedOutputPercent (текущий выход, %), fault, сетевые настройки |
| POST `/api/mode` | mode=manual/auto/auto_1h |
| POST `/api/execute` | без полей |
| POST `/api/preset` | slot=1…4, label, az, el (G-5500) |
| POST `/api/preset/run` | slot=1…4 |
| POST `/api/settings` | model=G5500/G800DXA/G800SA, rotorName, n1mmReport, n1mmPort, pstPort, reportPort, reportHost, n1mmManualFollow/pstManualFollow/gs232ManualFollow/rotctldManualFollow=true/false, externalAzMode=shortest/mechanical, speedEnabled=true/false, speedPercent/startSpeedPercent/approachSpeedPercent=1…100, accelerationMs/decelerationMs=100…10000, slowdownDegrees=1…90, coastDegrees=0…90, decelerationFactor=0.1…10 |
| POST `/api/target` | az и/или el; хотя бы одна ось, для G-800DXA и G-800SA — az; явная локальная команда выполняется сразу |

`GET /api/status` также возвращает `n1mmManualFollow`, `pstManualFollow`, `gs232ManualFollow`, `rotctldManualFollow`: `true` — автоследование в ручном режиме, `false` — подтверждение. Эти параметры доступны на контроллере и на HUD для принимаемых ими команд. `externalAzMode` в статусе и настройках задаёт обработку внешнего AZ: `shortest` — кратчайший доступный путь (по умолчанию), `mechanical` — механическая координата программы. Отрицательный AZ в командах GS-232 и PST задаёт явную механическую координату и принимается только внутри настроенного диапазона, в том числе при `shortest`. В PST `LP=1` добавляет к базовому азимуту 180°.

JSON: `ok`, `result`; 200 успешно/ожидание, 400 неверно/нет калибровки, 409 команда отложена приоритетом пресета. `GET /api/move?d=L/R/U/D/S/A/E` доступен для локального управления.

Клавиатурное удержание использует `POST /api/move` с `d=H`, ненулевыми 32-битными `client`, `session`, `gesture`, `serial`, маской осей `mask=1/2/3` и нормированными `az`/`el` от −1 до 1. Продлевайте команду чаще одного раза в секунду; веб-интерфейс делает это каждые 200 мс. Поля `gesture` и `serial` возрастают, одно нажатие сохраняет свой `gesture`. Для отпускания передайте те же идентификаторы, новый `serial`, нулевые `az`/`el` и `d=S` (все захваченные оси), `d=A, mask=1` (AZ) либо `d=E, mask=2` (EL). После завершения или истечения срока нажатие больше не возобновляется. Числовые цели, принятые после ручного вращения, не отменяются запоздавшим отпусканием.

### Параметры двух осей и аппаратная конфигурация

`/api/status` содержит объект `build` (версия `version` по SemVer, хеш коммита `commit`, признак изменённых исходников `dirty`, плата, дисплей, Bluetooth, силовой интерфейс, кнопка и основные GPIO), массив `axes` (положение, цель, калибровка, tracking/completed, направление, допуск, активность и выход скорости) и поля `azSpeedPercent`/`elSpeedPercent`, `azStartSpeedPercent`/`elStartSpeedPercent`, `azApproachSpeedPercent`/`elApproachSpeedPercent`, `azAccelerationMs`/`elAccelerationMs`, `azDecelerationMs`/`elDecelerationMs`, `azSlowdownDegrees`/`elSlowdownDegrees`, `azSpeedOutputPercent`/`elSpeedOutputPercent`.

`azCoastDegrees`/`elCoastDegrees` — настроенный угол выбега; `azDecelerationFactor`/`elDecelerationFactor` — коэффициент торможения. Они доступны в `GET /api/status` и `POST /api/settings`. `coastDegrees` и `decelerationFactor` без префикса относятся к AZ. Фактический допуск находится в `axes[].stopToleranceDegrees`. Настройки выбега меняются на самом контроллере поворотки.

`POST /api/settings` принимает настройки с префиксами `az`/`el` (кроме измеренных выходов). Поля без префикса также относятся к AZ. Если `speedPercent=50` и `azSpeedPercent=75` переданы вместе, весь запрос отклоняется без частичного изменения. `azSpeedEnabled` — алиас опционального `speedEnabled` Yaesu; у независимых приводов управление PWM является частью выбранного аппаратного интерфейса и не отключается настройкой. EL в моделях G-800DXA и G-800SA выключена. G-800SA сохраняет собственный набор калибровок и предустановок. Аппаратные поля доступны только для чтения; попытка изменить их через settings отклоняется.

`POST /api/speed` принимает `axis=az` / `el` и `value`: в простом режиме — процент выхода, в каскаде — °/с. Допустимый диапазон — от 5% до 100% верхнего предела оси (`speedLimit`). Уставка меняется без остановки текущего движения и сохраняется через 40 секунд после последнего изменения или перед штатной перезагрузкой. В контурах 100/200 Гц отложенная запись ожидает остановки всех осей. В `/api/status` и live-состоянии `axes[].speedSetpoint` и `speedLimit` содержат текущую уставку и её верхний предел, `speedAdjustable` — доступность регулировки. Команда доступна также через USB API контроллера. Для HUD и нерегулируемых выходов она отклоняется.

### API регуляторов движения

Каскадный режим распознаёт последовательность изменяющихся координат после второй команды. При периоде обновления до 1,5 с он продолжает слежение между пакетами, включая небольшие задержки доставки. Скорость оценивается по изменению координаты и ограничивается выбранной рабочей скоростью; прогноз положения ограничен одним периодом обновления, четвертью допуска положения и механическим диапазоном. При прекращении обновлений прогноз и скорость плавно уменьшаются; через 1,8–4,5 с (в зависимости от измеренного периода) возобновляется обычное завершение на последней точке. Повтор одной и той же координаты не продлевает поток. STOP останавливает выход немедленно и сбрасывает историю слежения.

`POST /api/settings` с `controlHz=50|100|200` меняет общую частоту контура и датчиков AZ/EL без перезагрузки, останавливает обе оси и сохраняет выбор. Во время автотюна смена недоступна; готовый результат после смены частоты требует нового подбора. HUD этот параметр не изменяет.

`GET /api/motion` возвращает настройки осей и `controlPeriodMs` — текущий номинальный период контура (20/10/5 мс). `GET /api/diagnostics` содержит `uptimeMs` для расчёта приращений счётчиков, `controlPeriodMs` и массив `motionTiming` для AZ и EL: `steps` — число выполненных шагов регулятора при активном движении, `maxIntervalMs` — максимальный интервал между ними, `lateSteps` — число интервалов больше выбранного периода, `sampleCount` — число измерений положения и `sampleMaxIntervalMs` — максимальный интервал измерений. Счётчики шагов накопительные с запуска или последней смены частоты и сохраняются при STOP; пауза между отдельными движениями в интервал контура не входит. Для фактической частоты сравнивайте приращение счётчиков за известное время непрерывного движения; одно поле `controlPeriodMs` частоту не подтверждает.

Для чтения через UART используйте `GET /api/diagnostics?axis=az` или `axis=el`: компактный ответ содержит `axis`, `controlPeriodMs` и объект `timing` с теми же счётчиками одной оси. Ответ помещается в одну страницу, поэтому изменение счётчиков между запросами не нарушает сборку JSON.

На платах с графическим экраном полный ответ `/api/diagnostics` также содержит `panel`: `renderMaxUs` — наибольшая длительность обслуживания LVGL в микросекундах; `touchReads` — число опросов тача, `touchErrors` — число недостоверных отсчётов, включая устаревший ввод; `touchHealthy`, `touchDown`, `x` и `y` — последний результат. Если `touchReads=0`, опрос ещё не запущен, в том числе в защитном режиме.

При UART 9600 бод большие JSON-ответы могут задерживать основной цикл. Во время движения считывайте телеметрию по HTTP/WebSocket, а подробные счётчики через UART — после STOP.

В каждом элементе `motionTiming` поля `feedbackRejected` и `feedbackInvalid` показывают число отброшенных скачков положения и аварий неверного показания. `rejectedAt` — время последнего отброшенного измерения от запуска, `rejectedIntervalMs` — интервал от последнего принятого измерения, `rejectedPosition` и `lastGoodPosition` — отвергнутое и предыдущее принятое положение в градусах. Повторное чтение одного измерения не увеличивает счётчик. Эти поля сохраняются при STOP и сбросе ошибки; при смене частоты или калибровки история начинается заново. Конечные скачки сначала отбрасываются без обновления возраста обратной связи; авария требует как минимум трёх разных измерений и 60 мс без правдоподобного положения на любой выбранной частоте. Нечисловое положение и потеря калибровки вызывают остановку сразу.

`GET /api/motion` возвращает массив `axes` с настройками AZ и EL: `regulatorMode` (`simple` / `cascade`), `ready`, `kickEnabled`, `holdEnabled` и числовые поля ниже. Числовые имена этого ответа начинаются с прописной буквы.

Для записи используйте `POST /api/settings`: `azRegulatorMode` / `elRegulatorMode`; остальные имена имеют вид `azMotion…` / `elMotion…`, например `azMotionVelocity=3`. Сохраняйте оси отдельными запросами, чтобы укладываться в лимит формы. Изменение коэффициентов PID, стартового импульса и окон фильтрации сохраняет выбранную рабочую скорость. Смена режима регулятора, `Velocity` или `OutputLimitPercent` сбрасывает её к настройке соответствующего режима. Готовность определяется автоматически. Прежнее поле `MotionReady` принимается для совместимости и не требует подтверждения. Некорректный запрос отклоняется целиком.

Смену модели и изменение параметров регулятора выполняйте отдельными запросами. При смене модели загружаются её сохранённые параметры; без такой записи используются параметры по умолчанию.

| Суффиксы после `Motion` | Значение |
|---|---|
| `KickEnabled`, `HoldEnabled` | Логические `true` / `false` |
| `OutputLimitPercent`, `KickPercent`, `MovementDegrees` | Общий предел, пусковой выход, угол подтверждения движения |
| `SustainingPercent` | Минимальный выход движения каскада, целый процент 0…100; 0 отключает ограничение снизу. Не выше `OutputLimitPercent`. Не действует при торможении, достижении позиции, STOP и защите. При слежении за изменяющейся координатой выход может снижаться ниже порога, чтобы не обгонять цель. |
| `Velocity`, `Acceleration`, `Deceleration`, `Jerk` | Ограничения профиля: °/с, °/с², °/с², °/с³ |
| `PositionKp`, `PositionKi`, `PositionKd` | ПИД положения: 1/с, 1/с², безразмерный D |
| `VelocityKp`, `VelocityKi`, `VelocityKd`, `Feedforward` | ПИД скорости и упреждение выхода |
| `PositionTolerance`, `HoldResumeDegrees`, `StoppedVelocity` | Допуск позиции, независимый порог коррекции удержания и порог остановки. Порог удержания может быть меньше допуска позиции; выход снимается в зоне половины порога или меньшего допуска |
| `KickMs`, `KickReleaseMs` | Время нарастания пуска и время его снятия. В обычном движении ошибка страгивания возникает через `max(KickMs, StallMs)`; автотюн использует отдельные ограниченные пробы |
| `VelocityWindowMs`, `DerivativeFilterMs`, `FeedbackTimeoutMs` | Окно скорости, фильтр D, срок свежести |
| `SettleMs`, `StallMs` | Подтверждение позиции и контроль заклинивания |
| `HoldReverseMs` | Пауза смены направления при активном удержании, 0–2000 мс; 0 отключает паузу, по умолчанию 300 мс. Остальные режимы сохраняют паузу 300 мс |

`axes[]` в `/api/status` и live-состоянии содержит `regulatorMode`, `motionReady`, `motionPhase`, `motionFault`, `measuredVelocity`, `requestedVelocity`, `profileAcceleration`, `holdEnabled`, `holdArmed`. Фазы: `idle`, `kick`, `run`, `braking`, `holding`, `fault`. Ошибки: `kick_start_timeout`, `feedback_stale`, `feedback_invalid`, `stalled`, `planner_error`.

Для проверки задержек `GET /api/status` возвращает `localFeedback` в порядке AZ, EL: `ageMs` — возраст последнего отсчёта АЦП, `maxIntervalMs` — наибольший интервал между отсчётами с запуска. Для отсутствующей локальной обратной связи передаётся `null`. Эти значения позволяют отделить задержку получения показаний от задержки передачи статуса по сети. При реверсе активное удержание использует `HoldReverseMs` и может корректировать ещё движущийся механизм; при 0 дополнительной паузы нет. Ручное вращение и наведение без активного удержания сохраняют паузу 300 мс и дополнительно ожидают остановки по измеренной скорости.

`POST /api/motion/reset` с `axis=az`, `el` или `all` снимает ошибку и останавливает выбранные оси; наведение не возобновляет. Настройки выполняются на контроллере поворотки. HUD передаёт сброс выбранной поворотке; для этого обе прошивки должны поддерживать сброс через HUD. Старый контроллер отклоняет неизвестную команду без запуска движения.

`GET /api/motion/autotune` возвращает фазу, `active`, `id`, ось (`0` AZ / `1` EL), режим, направление, пробный выход, причину остановки и ошибку проверки. Полный ответ содержит границы пробного участка и `measurements` для обоих направлений, в том числе при остановке с ошибкой. После успешного завершения добавляется `result` с предложенными параметрами. Выбранный этап `minimum` проверяет малую скорость отдельными пусками в обе стороны. Полный ответ содержит `minimumCandidate` (°/с для каскада, % для простого), `minimumSetpoint` (выбранная уставка в тех же единицах), `minimumVelocity` (наибольшая средняя измеренная скорость двух направлений, °/с), `minimumOutput` (%) и `minimumVerified`. Эти значения считаются результатом только при `phase=complete`; подтверждение `apply` также выбирает малую уставку скорости, если выполнялся её поиск. Верхний предел скорости сохраняется в предложенных параметрах. Краткое состояние `autotune` также включено в `/api/status` и live.

`action=start` принимает необязательное целое `tuneStages` — сумму флагов выбранных этапов:

| Флаг | Этап |
|---|---|
| 1 | Страгивание |
| 2 | Рабочие параметры / идентификация; автоматически включает флаг 1 |
| 4 | Минимальная устойчивая скорость |
| 8 | Слежение на малой скорости, только Cascade |
| 16 | Слежение на высокой скорости, только Cascade |

Без поля выбирается полный запуск: 31 для Cascade, 7 для Simple. Например, `tuneStages=4` ищет только минимум на сохранённом профиле, `8` или `16` настраивают одну скорость серий, `24` — обе скорости без повторной идентификации и поиска минимума. В полном ответе `options.tuneStages` содержит фактическую маску с зависимостями; активный компактный статус передаёт её как `stages`. Пустой набор, неизвестные биты и дробные значения отклоняются; в Simple флаги слежения исключаются, а запрос только слежения отклоняется. Короткая оценка шума и необходимая проверка результата выполняются автоматически. Параметры невыбранных этапов сохраняются; частичный запуск использует сохранённый профиль. Для частичного запуска пробный предел должен покрывать сохранённый минимальный выход движения и пусковой выход; ограничивающий их запрос отклоняется. Если выбран поиск страгивания, сохранённый пусковой выход можно измерить заново в пределах заданного максимума. В Simple уставки минимума ограничены пробным пределом и сохранённым минимальным выходом движения; измерение ждёт выхода из разгона. `minimumVerified=false`, если этап минимума не выполнялся; непроверенная скорость серий передаётся как 0. После изменения коэффициентов минимум перепроверяется только при выбранном флаге 4. `result` также содержит `holdEnabled` и `kickEnabled`, чтобы различать сохранённые и предложенные настройки частичного запуска.

В полном запуске каскада после `minimum` выполняется этап `tracking`: сравнение трёх вариантов P положения / PI скорости на восьми сериях каждого варианта (малая/высокая скорость × период 200/1500 мс × оба направления). Неустойчивый вариант прекращает оставшиеся пробы. Компактный статус содержит `trackingTrial` и `trackingTrials` (номер пробы и общее число: 12 при одной скорости, 24 при двух) во время подбора, а также `trackingPeriodMs`, `trackingDurationMs` и `trackingTravel` — период команд, полную длительность текущей серии в мс и её ход в градусах. Полный ответ (`options.methodVersion=14`) содержит объект `tracking`: `verified` (весь запуск завершён успешно), `candidate`, `case`, `selected` (индексы с нуля), `periodMs`, `casesPerCandidate` (4 или 8), фактические `slowVelocity` / `fastVelocity` в °/с и массив `candidates`. Массивы `warmupMs` и `durationMs` содержат время прогрева и полную длительность четырёх типов серии в порядке: малая/200 мс, малая/1500 мс, высокая/200 мс, высокая/1500 мс; для невыбранной скорости значения равны нулю. `reserve` — запас остановки при планировании в градусах. Ход серии равен её скорости, умноженной на `durationMs / 1000`. Для каждого варианта передаются `score` (меньше — лучше; сопоставим только внутри запуска), `meanError`, `peakError`, `overshoot` в градусах, `completed` (необходимо `casesPerCandidate`), `kicks`, `reversals`, `stoppedMs`, `rejected`, `failedCase` (номер отклонённой серии 0–7, иначе −1) и `reason` (причина отклонения варианта: `overshoot`, `oscillation`, `no_progress`, `travel_limit` или `insufficient_samples`). `meanError` усредняется по выбранным сериям и имеет смысл только для полностью прошедшего варианта. Ошибка и опережение считаются относительно непрерывной траектории в момент измерения датчика. Средняя ошибка и время остановок оцениваются после прогрева, только по свежим измерениям. По окончании серии выход снимается с ожиданием покоя; достижение последней промежуточной цели не является критерием серии. Точность одиночного наведения проверяется отдельно после выбора коэффициентов. Старые причины `endpoint_error` / `tracking_timeout` относятся к прежней методике ожидания последней цели. Данные незавершённого или отклонённого варианта не являются результатом. После выбора повторяются проверочные одиночные наведения; подтверждение малой уставки повторяется, если выбран поиск минимума. `tracking_unstable` означает, что ни один вариант не прошёл все серии; Apply недоступен. Исходные настройки возвращаются и при этой остановке. В Simple этап `tracking` пропускается, `tracking.verified=false`. Предел времени измерения — 120 с; при переходе к сериям общий предел рассчитывается по длительности всех выбранных проб с запасом на переносы и финальную проверку: от 480 до 1200 с. Поле `timeoutMs` полного ответа показывает текущий предел от начала запуска; переносы не обнуляют таймер. STOP и отмена действуют на всех этапах.

При нехватке хода автотюн останавливает пробу, ждёт покоя и возвращает ось в подготовленную позицию внутри исходного участка. Это промежуточное состояние `coast` / `reposition`, а не ошибка. Возврат может повторяться с меньшим рабочим выходом; предел числа возвратов отсутствует. Одна подготовка ограничена 60 с и общим временем запуска. Поиск минимума учитывает ход измерения и уже наблюдавшееся пусковое перемещение. Если изменившийся запас остановки требует более короткой траектории серий, их скорости пересчитываются и сравнение трёх вариантов выполняется заново в одинаковых условиях. При отказе подготовки полный `failure` может содержать `requiredTravel` / `availableTravel` в градусах и `preparationAttempts` (число возвратов). Поле `preparationLimit` больше не передаётся. `stopping_distance` означает, что даже из крайней допустимой исходной позиции измеренный запас остановки не оставляет хода для достоверной пробы.


Отсутствие движения на пробном малом выходе не считается самостоятельной аварией привода: поиск страгивания повышает уровень до пробного предела, поиск минимума пробует большую уставку, а серия без движения отклоняет текущий вариант коэффициентов и переходит к следующему. Если выбран этап страгивания, неудачный пуск при поиске минимума может повысить пусковой выход; новое предложение проходит повторное проверочное наведение. Параметры невыбранных этапов сохраняются. При нехватке места возврат повторяется глубже внутри заданного участка. Пределы выхода, участка и времени сохраняются; недостоверный датчик, STOP и выход за границы прекращают движение.

При ошибке во время процедуры полный ответ (`phase=failed`) также содержит `failure` — снимок до отключения и возврата исходных настроек: `phase`, `motionPhase`, `elapsedMs`, `position`, `target`, `velocity`, `output`, `threshold` (порог покоя автотюна), `stoppedVelocity` (порог регулятора), `direction`, `tracking` и `velocityWindowMs`. Это значения в момент отказа, а не текущая телеметрия. Для ожидания покоя используется `coast_timeout`, для незавершённой перестановки — `reposition_timeout`, для проверочного наведения — `validation_timeout`. В веб-интерфейсе показаны этап, выход, скорость и пороги; цель и ошибка позиции показываются для этапов с целевой координатой. Без сохранённого снимка, в том числе при ошибке записи настроек после применения, поле `failure` отсутствует. Старый `settle_timeout` обозначает общую ошибку прошивок без такой детализации.

`POST /api/motion/autotune` с `action=center&axis=az|el` запускает однократное наведение выбранной оси к середине её откалиброванного диапазона, без удержания после достижения. Используются сохранённые настройки движения; `outputLimit` пробного автотюна к этому наведению не относится. Команда переводит контроллер в ручной режим, останавливает предыдущее движение обеих осей, снимает удержание и отменяет ожидающие команды. Нужны свежие откалиброванные измерения и отсутствие ошибок; во время активного автотюна команда недоступна. Можно передать `rangeRevision`; устаревшая ревизия отклоняется. STOP останавливает наведение.

`POST /api/motion/autotune` принимает `action=start` с `axis=az|el`, `mode=simple|cascade`, `travel` (ход в каждую сторону), `outputLimit` и `id` из последнего статуса. Успешный запуск переводит контроллер в ручной режим, отменяет ожидающие команды и увеличивает `id`; повтор старого запроса не запускает новую процедуру. `action=cancel` останавливает активную процедуру; `action=apply&id=…` применяет только готовый результат указанного запуска. Изменённые параметры, калибровка или диапазон требуют нового автотюна. Для сохранения через HTTP используйте контроллер поворотки; HUD не пересылает эти запросы. Во время автотюна `/api/settings` возвращает `busy`.

Прежние поля процентов и ручного выбега относятся к простому варианту. `startSpeedPercent` / `elStartSpeedPercent` сохранены для совместимости хранения; новый пуск задаётся через `MotionKickPercent` и `MotionKickEnabled`. На нерегулируемых выходах пусковой импульс, S-профиль и каскад недоступны.

### Ограничения HTTP-клиента

Передавайте POST-формы с `application/x-www-form-urlencoded`. Полный запрос вместе с заголовками и телом — до 4096 байт, суммарно до 40 параметров query/body; для `/api/hardware` и его подпутей — до 96; после URL-декодирования ключ — до 32 байт, значение — до 128 байт. Произвольные файлы и chunked-запросы не поддерживаются; для прошивки используйте отдельный [блочный API OTA](../maintenance/ota.md#http-api).

При обрыве или тайм-ауте запроса управления сначала прочитайте состояние: команда могла выполниться до потери ответа. Для HUD дополнительно дождитесь результата по `requestId`, как описано в [API HUD](../control/hud.md#http-api).


## HTTP API оборудования

`GET /api/hardware` возвращает сохранённые, действующие и подтверждённые параметры, состояние пробного запуска, причину восстановления, свободную внутреннюю память, `token` текущего запуска и `generation` конфигурации. Поля `failureCount`, `failureLimit`, `failureResetMs` и `lastFailure` показывают накопленные сбои, порог восстановления, интервал нормальной работы до сброса и последнюю причину сбоя. Объекты `configured`, `effective` и `confirmed` содержат карту `pins`; `effective` показывает реально применённую распиновку.

`GET /api/hardware?view=form` возвращает те же признаки и диагностические поля, но из трёх конфигураций содержит только редактируемую `configured`. Этот вариант подходит для периодического обновления формы оборудования.

`GET /api/hardware/reboots` доступен также в режиме восстановления. Поле `current` содержит `reason` и `code` текущего запуска, `recoveryReason` — причину включения восстановления. Объект `history` содержит `available`, `count` и до 20 записей `entries`, начиная с последней. В каждой записи: `epoch` (Unix-время; 0, если часы не были синхронизированы), `reason` и `code`. При недоступности хранилища `available` равен `false`.

Запросы изменения используют POST с `Content-Type: application/x-www-form-urlencoded` и актуальными `token` / `generation`:

| Адрес | Действие |
|---|---|
| `/api/hardware` | Сохранить переданные поля оборудования и GPIO, затем перезапустить |
| `/api/hardware/probe` | Проверить обычный обработчик POST и запись NVS перед подтверждением |
| `/api/hardware/confirm` | Подтвердить проверенный пробный запуск и перезапустить |
| `/api/hardware/rollback` | Вернуть подтверждённую конфигурацию и перезапустить |
| `/api/hardware/recovery` | Перезапустить в режиме восстановления |

При применении оборудования через `/api/hardware` или `/api/hardware/rollback` ответ `confirmationRequired` указывает, требуется ли пробный запуск после перезапуска. Если сохранённые параметры совпадают с последними подтверждёнными, он равен `false`: достаточно одного перезапуска, без `/probe` и `/confirm`. Новые параметры или отсутствие подтверждённой конфигурации требуют пробного запуска (`true`).

При сохранении обязательны `token`, `generation` и хотя бы одно изменяемое поле. Пропущенные поля сохраняют значения текущей выбранной конфигурации. Поля оборудования: `driveInterface` (0 Yaesu, 1 LEFT/RIGHT + отдельный PWM, 2 LEFT_PWM/RIGHT_PWM + ENABLE, 3 DIR + PWM), `simulation`, `bluetoothEnabled`, `bluetoothMode` (1 HC-05, 2 SPP, 3 автоматически), `forceApSta`, `buttonGpio`, `buttonActiveLow`, `buttonPullup`, `pwmInverted`. Логические поля принимают 0 или 1.

Датчики положения задаются полями `azSensor` / `elSensor`: 0 — потенциометр ADC, 1 — MT6701, 2 — AS5600. Поля `azSensorAddress` / `elSensorAddress` содержат десятичный 7-битный адрес I²C (обычно 6 для MT6701, строго 54 для AS5600), `azSensorZero` / `elSensorZero` — программный ноль в отсчётах датчика (0…16383 или 0…4095). При выборе энкодера ADC этой оси не требуется. Общая пара SDA/SCL допустима только для разных адресов. Поля `azSensorInverted` / `elSensorInverted` задают направление сигнала для всех датчиков: 0 — прямое, 1 — обратное (исходный отсчёт уменьшается с ростом реального угла). Смена типа, GPIO, адреса, нуля или направления сбрасывает калибровку соответствующей оси. См. [подключение и калибровку](../setup/position-sensors.md).

`GET /api/adcdiag` возвращает `azSensor` / `elSensor` (`ADC`, `MT6701`, `AS5600`), `azRaw` / `elRaw` (исходный отсчёт), `azValue` / `elValue` (значение для калибровки с учётом программного нуля и направления). Для потенциометра `Value` измеряется в мВ; для энкодера — в его отсчётах. Прежние `azMv` / `elMv` для энкодера равны `null`. При ошибке чтения `Value` равен −1. В `/api/status` и `/api/config` поля `azSensor` / `elSensor` указывают источник положения.

Для GPIO используйте поля `pin.<имя>` со значением `−1` или номером GPIO:

| Группа | Имена |
|---|---|
| Энкодеры I²C | `azSensorSda`, `azSensorScl`, `elSensorSda`, `elSensorScl` |
| Привод и ADC | `azAdc`, `elAdc`, `azNegative`, `azPositive`, `elNegative`, `elPositive`, `azSpeedEnable`, `elSpeedEnable` |
| UART0 и HC-05 | `uartRx`, `uartTx`, `hc05Rx`, `hc05Tx`, `hc05State` |
| Индикация | `rgb`, `led` |
| TFT и тачскрин | `tftMosi`, `tftSck`, `tftMiso`, `tftCs`, `tftDc`, `tftRst`, `touchCs`, `touchIrq` |
| LCD1602 | `lcdRs`, `lcdE`, `lcdD4`, `lcdD5`, `lcdD6`, `lcdD7` |

GPIO кнопки передаётся прежним полем `buttonGpio`. `GET /api/hardware/pins` возвращает `roles` с именем, группой, типом, необязательностью и начальным GPIO сигнала, а также `gpios` с номером, возможностями `caps` и владельцем `owner`. Биты `caps`: 1 — вход, 2 — выход, 4 — ADC1, 8 — внутренняя подтяжка. `owner` обозначает встроенную периферию или аппаратный резерв. Занятость настраиваемыми сигналами определяется текущими значениями `pins` и режимом оборудования.

Во всех PWM-интерфейсах ENABLE оси необязателен: `−1` отключает GPIO, назначенный вывод активен HIGH при движении. В DIR_PWM и SEPARATE_PWM передавайте `pin.azEnable` / `pin.elEnable`; в BTS7960 — `pin.azSpeedEnable` / `pin.elSpeedEnable`, как и раньше. Поля скорости SEPARATE_PWM и DIR_PWM остаются обязательными.

Пример частичного изменения на S3 после чтения актуальных `token` и `generation`:

```sh
curl --data 'token=123&generation=2&pin.azAdc=1' http://192.168.4.1/api/hardware
```

Весь запрос проверяется и сохраняется целиком. Ошибки GPIO возвращают HTTP 400 с `error`, `field`, `gpio` и `owner`; конфликтующее поле можно исправить без изменения сохранённых настроек. Повторяющиеся и неизвестные поля отклоняются. Ошибки сохранения возвращают 503; устаревшие параметры запуска или ещё не готовое подтверждение — 409.

Остальные POST передают только `token` и `generation`. Успешное подтверждение требует предварительного успешного `/api/hardware/probe` и достаточного запаса памяти. В восстановлении `/api/hardware/probe` недоступен: сначала примените оборудование. Если параметры отличаются от подтверждённых, после перезапуска потребуется пробный запуск.

## Расширения ручного управления HUD

Существующие кадры HUD/1 с типами 1–10 сохраняют формат. Новые типы:

| Тип | Содержимое после стандартного заголовка |
| --- | --- |
| 11 ExtendedQuery | Запрос поддержки расширенного состояния |
| 12 ExtendedState | Полное состояние и байт маски известных целей AZ/EL |
| 13 ExtendedSubscribe | Подписка на расширенную телеметрию |
| 14 ExtendedTelemetry | Ревизия, компактное состояние и маска известных целей |
| 15 Manual | gesture:u32, mask:u8, release:u8, AZ:f32, EL:f32 |
| 16 ManualAck | gesture:u32, result:u8 |

Биты mask: 1 — AZ, 2 — EL. Значения скоростей конечные, от −1 до +1; масштаб
применяется к рабочей скорости без записи настроек в NVS. Заголовок передаёт
идентичность и загрузочную сессию обоих устройств, последовательный номер и
срок действия команды. CRC и порядок байтов соответствуют HUD/1.


Полный двоичный формат и версии: [hud.hpp](../../G5500_Fork/hud.hpp). Пользовательские действия описаны в [руководстве CrowPanel](../boards/crowpanel-21.md#ручное-движение).

### Кнопки и калибровка джойстика

`GET /api/hardware` возвращает в настройках оборудования `localInputMode` (0 — выключено, 1 — кнопки, 2 — джойстик, 3 — кнопки и джойстик одновременно), `localAzInvert` / `localElInvert` (0/1), `localAzMin/Center/Max`, `localElMin/Center/Max`, `localDeadzone` и `localHysteresis` (12-битные отсчёты ADC). GPIO находятся в `pins.localAzNegative`, `localAzPositive`, `localElNegative`, `localElPositive`, `localAzAdc`, `localElAdc`. Запись выполняется частичными полями через `POST /api/hardware` с актуальными `token` и `generation`; изменения требуют перезапуска и подтверждения оборудования.

После сохранения и подтверждения GPIO джойстика доступны POST-запросы с теми же `token` и `generation`:

| Путь | Действие |
|---|---|
| `/api/hardware/joystick/start` | Остановить удержание и включить измерения с блокировкой движения |
| `/api/hardware/joystick/poll` | Продлить измерения и получить `raw: [AZ, EL]`; −1 обозначает неподключённый вход |
| `/api/hardware/joystick/cancel` | Завершить измерения без записи калибровки |

Опрос нужен чаще одного раза в 2 секунды. После его прекращения блокировка измерений снимается, новое удержание требует нейтрали. Клиент отдельно фиксирует центр и крайние отсчёты и сохраняет их через настройки оборудования. Калибровка джойстика на HUD относится к входам пульта; калибровка положения поворотки остаётся на её контроллере.

## Мастер настройки и адреса сети

`GET /api/setup` возвращает версию состояния, `required`, `paused`, номер `step`, `generation`, готовность текущего шага `ready` токен проверочной сессии, выбранные `driveInterface` и `simulation`, `restartRequired` (сохранённые параметры ожидают перезапуска) и `pendingNext` (продолжение после перезапуска). `POST /api/setup` принимает `action=start|resume|back|advance|pause|complete|arm|renew|begin_save|end_save|apply|drive|motion`. Для перехода вперёд нужна актуальная `generation`; готовность проверяет устройство. Номера шагов: 0 сеть, 1 роль, 2 модель, 3 оборудование, 4 местные входы, 5 калибровка, 6 регуляторы, 7 программы, 8 поворотки HUD, 9 завершение, 10 закончено. Неприменимые шаги пропускаются.

Поля `motionAllowed`, `motionConfirmed` и `motionCanConfirm` описывают доступ к обычному движению при незавершённом мастере. В применённой локальной имитации доступ автоматический. Для физического привода `POST /api/setup` с `action=motion`, актуальной `generation` и `confirmed=1` сохраняет явное подтверждение готовности; оборудование должно быть сохранено и подтверждено, привод остановлен. `confirmed=0` отзывает разрешение и останавливает движение. Этот запрос доступен по HTTP без проверочного токена, в том числе при отложенном мастере. Он не завершает мастер и не снимает блокировки оборудования, ошибок привода или калибровки. Смена роли, модели, оборудования или диапазонов отзывает подтверждение. Старые сохранённые состояния мастера загружаются без разрешения физического движения.

На шаге 2 действие `drive` с актуальной `generation`, `setupToken`, `driveInterface=0|1|2|3` (Yaesu, отдельный PWM, BTS7960, DIR + PWM) и `simulation=0|1` сохраняет выбор для последующего применения оборудования. Это не инициализирует моторные выходы и не перезапускает устройство.

Сохранение нескольких форм шага начинается с `begin_save` с действующим `setupToken`. В этом режиме сеть, роль и оборудование откладывают перезапуск, пока клиент записывает остальные формы. `end_save` завершает запись. При `restartRequired=true` действие `apply` с тем же токеном сохраняет продолжение и запускает один перезапуск; иначе используется `advance` или `complete`. После перезапуска мастер ждёт фактической готовности шага и продолжает настройку. `pause` сохраняет этап и применяет ожидающий перезапуск. Без этой последовательности отдельные API настроек сохраняют прежнее поведение.

Сессия настройки `setupToken` не истекает от задержек связи: введённые значения можно сохранить и продолжить шаг после восстановления соединения. Для явного запуска проверки на шаге калибровки, регуляторов или завершения сначала передайте `action=arm` с `setupToken`. Ответ содержит отдельный `testToken`. Проверочные HTTP-команды движения требуют оба поля: `setupToken` и `setupTestToken=testToken`. Продлевайте только запущенную проверку через `action=renew` с обоими токенами не реже раза в секунду. Через 1,5 секунды без продления проверка отменяется и моторные выходы отключаются. Продление старого допуска и запоздавшие команды не возобновляют движение; новый запуск требует `arm` и нового `testToken`. STOP доступен всегда. На шаге программ с тем же токеном также можно включить ручной режим. Обычные команды программ, WebSocket и местных входов не получают проверочный допуск. Состояние мастера сохраняется после перезапуска; токен сессии не сохраняется.

`GET /api/network` также возвращает `choice` и объекты `wifi`/`eth` с `mode`, `address`, `mask`, `gateway`, `dns1`, `dns2`. `POST /api/network` принимает `choice=0…4` (роутер Wi-Fi, AP, общая AP, клиент общей AP, Ethernet), `wifiMode`/`ethMode=dhcp|static` и поля с префиксом интерфейса: например, `wifiAddress`, `wifiMask`, `wifiGateway`, `wifiDns1`, `wifiDns2`. Сохранение перезапускает устройство. Отсутствующая адресная конфигурация означает DHCP. SSID и пароли по-прежнему задаются через `/api/wifi` и `/api/ap`.

`POST /api/hardware` также принимает поля `mb.pc`, `mb.bus`, `mb.address`, `mb.node`, `mb.first`, `mb.count` для совместной проверки и применения GPIO и параметров Modbus. Отдельный `/api/hardware/modbus` сохраняется.

`GET /api/hardware/modbus` также возвращает `uart0Baud`, `uart0Parity`, `uart0StopBits`, `uart1Baud`, `uart1Parity`, `uart1StopBits`. `POST` на тот же адрес принимает эти поля с актуальными `token` и `generation`; пропущенные параметры сохраняются. Для совместного применения через `/api/hardware` используйте префикс `mb.`, например `mb.uart0Baud`. Скорости: 1200, 2400, 4800, 9600, 19200, 38400, 57600, 115200. Чётность: 0 — нет, 1 — чётная, 2 — нечётная; стоп-биты: 1 или 2; битов данных всегда 8. Неверные параметры линии возвращают HTTP 400 / `invalid_uart_settings`. Изменение протокола `pc` или `bus` не изменяет настройки линии. Успешная запись проверяется чтением и требует перезапуска.


`GET /api/motion/coast` возвращает фазу и результаты измерения выбега по осям и направлениям: градусы и секунды. `POST` принимает `action=start|cancel|apply`, `axis=0|1`; для запуска также `direction=0|1` (−/+), `travel=5…90` градусов. Измерение доступно физической оси с фиксированной скоростью, действующей калибровкой, свежими показаниями и запасом хода. Проба ограничена 30 секундами. Применение требует измерений в обоих направлениях и сохраняет больший угол; время не используется как упреждение. Отмена и ошибочный замер не заменяют сохранённый угол.

## Ориентация экрана и тача

`GET /api/hardware/display` возвращает доступность `supported`, тип `displayKind`, текущие `width` / `height`, признаки `storageOk` / `restartRequired`, `token` текущего запуска и отдельную `revision` ориентации. При `supported=false` изменение недоступно. При `storageOk=false` загружены начальные значения профиля; можно сохранить нужную ориентацию заново.

| Поле | Значения |
|---|---|
| `screenRotation`, `touchRotation` | 0, 90, 180, 270 градусов по часовой стрелке |
| `screenMirrorX`, `touchMirrorX` | 0/1: отражение слева направо |
| `screenMirrorY`, `touchMirrorY` | 0/1: отражение сверху вниз |

`screen*` меняет изображение; соответствие тача автоматически учитывает это преобразование. `touch*` — дополнительная коррекция ориентации самого сенсора. Нулевые значения означают начальную ориентацию выбранного профиля, отражения применяются после поворота.

`POST /api/hardware/display` принимает form-urlencoded с актуальными `token` и `revision` и одним или несколькими полями из таблицы. Пропущенные параметры сохраняются. Успешный ответ — `{"ok":true,"error":""}`. При изменении параметров устройство останавливает движение, проверяет сохранение и перезапускается; новое преобразование действует после запуска. Повторная запись уже действующих параметров не требует перезапуска. Настройки хранятся отдельно от пробной аппаратной конфигурации, с собственной ревизией для каждого типа экрана.

Ошибки: 400 — `invalid_form`, `invalid_rotation`, `invalid_mirror`; 409 — `display_unavailable`, `stale_configuration`, `restarting`; 503 — `storage_failed`. Блокировка OTA также распространяется на этот адрес. Практические шаги: [поворот и отражение](../control/display.md#поворот-и-отражение).

### Память и предыдущий отказ выделения

`GET /api/diagnostics` возвращает `networkMemoryLimited`, `udpDropped` (пакеты логгеров с недопустимым размером) и `tcpAborts` (принудительно закрытые сеансы rotctld). `GET /api/diagnostics?previousFailure=0` или `1` читает первый отказ предыдущего запуска размером менее 1024 байт или от 1024 байт соответственно. Если `ready=true`, ответ содержит `size`, `caps`, `free`, `largestBlock`, `task`, `function`, `pc` и `elf` — SHA-256 ELF, необходимый для расшифровки адресов стека. При отсутствии корректной записи возвращается `ready=false`.

Эти контексты также доступны в `previousAllocations` ответа `GET /api/hardware/reboots`, включая recovery. Запись переживает программный перезапуск; после отключения питания её наличие не гарантируется.
