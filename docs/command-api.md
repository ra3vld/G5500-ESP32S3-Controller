# Управление без браузера: UART/USB, UDP и TCP

Командный API доступен во всех конфигурациях, включая обычные сборки с веб-интерфейсом. Он позволяет управлять повороткой, менять настройки, калибровать оси, работать с HUD и восстанавливать доступ без браузера. GS-232, Hamlib и UDP-протоколы логгеров сохраняются.

## Подключение

- UART0/USB–UART: **9600, 8N1**, существующие выводы GS-232 выбранной платы.
- Native USB на ESP32-S2/S3: отдельный порт USB, доступный также при использовании UART0 для HUD или привода CrowPanel. После первого запроса `@` обычный журнал перестаёт выводиться в этот USB-порт до перезапуска; его можно читать через API.
- UDP: порт **4535**; запросы отправляются устройству, ответы приходят на исходный порт клиента.
- TCP: существующий порт **4533**, общий с GS-232/Hamlib.

Если UART0 переключён на HUD/1, он работает на 115200 и занят межплатным соединением. Для командного API используйте native USB или сеть. В режиме восстановления UART0 возвращается к консоли 9600, независимо от сохранённой роли HUD.

На выводах UART допустимы логические уровни 3,3 В. Распиновка приведена в [описании оборудования](hardware.md) и [инструкции классического ESP32](classic-esp32.md).

## Утилита для компьютера

Запускайте из корня проекта с Python 3. На Linux/macOS дополнительные пакеты для UART не нужны. Для последовательного порта Windows установите `python -m pip install pyserial`. Закройте другие программы, использующие этот же COM-порт.

```sh
python3 tools/controller_api.py --serial /dev/ttyUSB0 GET /api/status
python3 tools/controller_api.py --serial /dev/ttyACM0 GET /api/diagnostics
python3 tools/controller_api.py --udp 192.168.4.1 GET /api/hardware
python3 tools/controller_api.py --tcp 192.168.4.1 POST /api/mode mode=auto
python3 tools/controller_api.py --udp 192.168.4.1 POST /api/target az=120 el=30
python3 tools/controller_api.py --serial /dev/ttyUSB0 POST /api/move d=S
```

Замените порт и адрес своими значениями. Значения с пробелами заключайте в кавычки: `"ssid=Моя сеть"`. Настройки можно передавать несколькими запросами, если форма целиком превышает лимит 1024 байта. Каждый запрос проверяется и применяется целиком.

Для наблюдения с записью и немедленным сохранением каждой строки:

```sh
python3 tools/controller_api.py --serial /dev/ttyUSB0 --watch 10 --duration 86400 --log memory.jsonl GET /api/diagnostics
```

Утилита сама открывает сессию, повторяет потерянный запрос с тем же идентификатором и собирает страницы ответа. При смене устройства или сессии она сообщает об ошибке; перед повтором действия прочитайте состояние устройства.

## Варианты методики автотюна без перепрошивки

Для каждого запуска можно изменить методику измерения через тот же API по USB, UDP, TCP или HTTP. Опции действуют только в текущем запуске, не сохраняются в настройках и не наследуются следующим запуском. Сначала остановите обе оси, отключите удержание, выберите ручной режим и прочитайте идентификатор последней процедуры:

```sh
python3 tools/controller_api.py --serial /dev/ttyUSB0 GET /api/motion/autotune full=1
python3 tools/controller_api.py --serial /dev/ttyUSB0 POST /api/motion/autotune action=start axis=az mode=cascade id=0 travel=60 outputLimit=50 tuneSearchStartPercent=10 tuneSearchStepPercent=5 tuneWorkingFraction=0.7 tuneLambdaFactor=2
python3 tools/controller_api.py --serial /dev/ttyUSB0 GET /api/motion/autotune full=1
python3 tools/controller_api.py --serial /dev/ttyUSB0 POST /api/motion/autotune action=cancel
```

Замените `id=0` на прочитанный `id`, а `mode` — на сохранённый режим выбранной оси. Идентичный повтор старого запроса новый запуск не создаёт. Для следующей гипотезы отмените или дождитесь завершения текущей процедуры, прочитайте новый `id` и передайте полный набор нужных отличий от значений по умолчанию. В автоматических сценариях передавайте `action=cancel id=…`: отмена с устаревшим идентификатором отклоняется и не затрагивает новый запуск. Отмена без `id` сохраняет обычное действие кнопки «Отменить».

| Поле | По умолчанию | Допустимо | Что изменяет |
|---|---:|---:|---|
| `tuneSearchStartPercent` | 5 | 1…100, не выше `outputLimit` | Первый постоянный выход поиска страгивания |
| `tuneSearchStepPercent` | 5 | 1…20 | Шаг поиска страгивания и повышения верхнего рабочего уровня, в процентных пунктах |
| `tuneStartupObservationMs` | 500 | 100…2000 | Минимальное наблюдение уровня без движения; фактический интервал также учитывает задержку датчика и ограничен сроком пуска |
| `tunePlateauMinMs` | 200 | 160…1000 | Минимальное окно измерения устойчивой скорости; подтверждается вторым окном |
| `tunePlateauTimeoutMs` | 2500 | 1000…10000 | Срок поиска устойчивого рабочего участка, затем минимальный выход повышается |
| `tuneWorkingFraction` | 0,5 | 0,1…1 | Желаемая доля разрешённого выхода для верхней рабочей точки; сохранённый рабочий процент также учитывается |
| `tuneLambdaFactor` | 1 | 0,5…4 | Множитель времени отклика PI скорости: больше — спокойнее настройка каскада |
| `tunePositionGainFactor` | 1 | 0,25…2 | Множитель предложенного P положения каскада |

`tunePlateauTimeoutMs` должен быть не меньше `2 × tunePlateauMinMs + 200`. Неизвестное поле с префиксом `tune` или неверное значение отклоняет запрос целиком. Ответ `full=1` содержит фактически принятые `options` и версию `options.methodVersion` для сопоставления результатов. Компактные статусы остаются короткими.

Изменение гипотезы не отключает свежесть датчика, контроль другой оси, границы пробного участка, предел выхода, паузу реверса и общий срок процедуры 120 секунд. Длинные окна требуют большего свободного хода; процедура может безопасно отказаться от результата, если он не помещается. Малый `tuneLambdaFactor` и большой `tunePositionGainFactor` увеличивают риск раскачки. Каждая методика проходит обычную проверку наведения в обе стороны; результат применяется отдельным `action=apply id=…`, который сохраняет параметры. Для сравнения гипотез до применения используйте полные ответы с измерениями и предложением; сохранённые настройки восстанавливаются после каждой процедуры.

### Сравнение с записью результатов

Для сравнения создайте файл `variants.json`, например:

```json
{
  "baseline": {
    "axis": "az", "mode": "cascade", "travel": 60, "outputLimit": 50
  },
  "calmer": {
    "axis": "az", "mode": "cascade", "travel": 60, "outputLimit": 50,
    "tuneLambdaFactor": 2, "tunePositionGainFactor": 0.7,
    "tunePlateauMinMs": 400, "tunePlateauTimeoutMs": 4000
  }
}
```

Проверьте файл без подключения, затем запустите один выбранный вариант:

```sh
python3 tools/autotune_experiment.py variants.json calmer --dry-run
python3 tools/autotune_experiment.py --serial /dev/ttyUSB0 --log calmer.jsonl variants.json calmer
```

Запуск приводит ось в движение. Подготовьте свободный участок с запасом на выбег и используйте один источник управления. Параметры `travel` и `outputLimit` задают разрешённый пробный ход и предел выхода. Для следующего варианта верните привод в сопоставимое начальное положение. Вместо USB можно указать `--udp HOST` или `--tcp HOST`.

Утилита записывает исходный вариант, положение, измеренную скорость, выход, фазы и полный итог в новый JSONL-файл. Сравнивайте оба направления, измеренные рабочие скорости, выбег и `validationError`; успешное завершение само по себе не доказывает устойчивость под нагрузкой. Чтение через USB на 9600 бод занимает время, поэтому журнал служит для сравнения проб, а регулятор продолжает работать со своим периодом.

Результат автоматически не применяется. Для сохранения выбранного результата используйте `POST /api/motion/autotune action=apply id=…`, взяв `id` из итога последнего запуска. При Ctrl+C или таймауте утилита пытается отменить свою процедуру; при потере связи отмена может не дойти. Встроенные ограничения пробного хода, выхода и длительности сохраняются. Утилита не меняет настройки защит, калибровку или режим сети.

## Операции

Имена путей и полей соответствуют [API управления](usage.md#веб-api), [настройкам оборудования](configuration.md#http-api-оборудования) и [API HUD](hud.md#http-api). В командном API все изменения выполняются методом **POST**, включая операции, исторически доступные в вебе через GET.

| Операция | Метод и путь / параметры |
|---|---|
| Текущее положение, цели, режим, блокировка, ошибка | GET `/api/status` — компактный ответ с двумя осями, ожидающей целью и таймером режима; `view=axis&axis=az` или `el` возвращает фазу, скорость и ошибку отдельной оси |
| Расширенные настройки, предустановки, диапазоны | GET `/api/config` |
| Наведение, направления, STOP | POST `/api/target`, `/api/move` |
| Режим, подтверждение цели, предустановки | POST `/api/mode`, `/api/execute`, `/api/preset`, `/api/preset/run` |
| Настройки и порты | POST `/api/settings`; `commandPort=…` задаёт порт командного UDP |
| Параметры регуляторов | GET `/api/motion`, POST `/api/settings` с полями AZ/EL |
| Автотюн | GET `/api/motion/autotune`; `full=1` возвращает полный результат; POST того же пути запускает, отменяет или применяет результат |
| Сброс ошибки привода | POST `/api/motion/reset` с `axis=az`, `el` или `all` |
| Диапазоны и произвольные точки | POST `/api/azrange`, `/api/elrange`, `/api/azcal`, `/api/elcal`; таблицы читаются GET `/api/azcal`, `/api/elcal` |
| Двухточечная калибровка | POST `/api/calmode m=2`, затем POST `/api/cal2 p=O`, `F`, `O2`, `F2` |
| Многоточечная калибровка | POST `/api/calmode m=multi`; POST `/api/cal p=az0` и другие точки стандартной таблицы; для произвольного диапазона — `/api/azcal` или `/api/elcal` |
| Сброс калибровки | POST `/api/calreset axis=az mode=2`; `axis=el`, `mode=multi` выбирают другую таблицу |
| Состояние Wi-Fi, IP-адреса, RSSI и порты | GET `/api/network` |
| Wi-Fi и пароль AP | POST `/api/wifi ssid=… pass=…`, POST `/api/ap pass=…`; устройство перезапускается |
| Роль, поиск и каталог HUD | GET/POST `/api/device`, GET/POST `/api/hud/peers`, POST `/api/hud/discover`, `/api/hud/select` |
| Результат команды HUD | GET `/api/hud/command id=…` |
| ADC, память и отказы выделения | GET `/api/adcdiag`, `/api/diagnostics`; `failure=0` или `1` возвращает сохранённый отказ малого или большого выделения |
| Журнал, причина и история перезапусков, RSSI | GET `/api/diaglog`, `/api/resetreason`, `/api/resethistory`, `/api/rssi range=…` |
| Очистка журнала или истории | POST `/api/diaglog/clear`, `/api/resethistory/clear` |

Каталог `/api/hud/peers` в командном API по умолчанию возвращает одну запись; следующие записи запрашивайте с `offset=1`, `2` и далее до `total`. Это позволяет читать каталог при обновляющейся телеметрии.

Калибровку и настройку регуляторов выполняйте на контроллере поворотки. HUD сохраняет ограничения существующего API. При автотюне просматривайте короткий статус, полный результат запрашивайте после остановки процедуры. Если изменяющийся большой документ не удаётся прочитать согласованно, утилита сообщает об этом.

Порт командного UDP не должен совпадать с портами HUD, N1MM, PST, ответа PST (`pstPort+1`) или отчётов. Также зарезервированы UDP 3232 (ArduinoOTA), 5353 (mDNS) и, в сборках с вебом, 32769 (служба live). Изменение `commandPort` применяется через 1,5 секунды после ответа; следующие подключения выполняйте к новому порту.

## Оборудование и восстановление

1. Прочитайте GET `/api/hardware`. Ответ содержит `token`, `generation`, `configured`, `trial`, `recovery`, `reason`, `ready`. Параметр `view=confirmed` или `view=effective` выбирает подтверждённую или действующую конфигурацию.
2. Передайте POST `/api/hardware` с `token`, `generation` и изменяемыми аппаратными полями из [описания API оборудования](configuration.md#http-api-оборудования). Для сборки без Bluetooth укажите `bluetoothEnabled=0`.
3. После перезапуска повторно прочитайте `/api/hardware`: токен запуска изменился. Пока идёт пробный запуск, движение заблокировано.
4. Дождитесь `ready=true`, выполните POST `/api/hardware/probe` с текущими `token` и `generation`, затем POST `/api/hardware/confirm` с теми же значениями. После подтверждения устройство перезапустится.

Для переназначения GPIO передавайте `pin.<имя>=GPIO`, например `pin.azAdc=1`. `GET /api/hardware/pins` возвращает доступные GPIO, встроенные соединения и значения по умолчанию. Частичные изменения и чтение `configured.pins` доступны через те же операции, что и в HTTP API.

POST `/api/hardware/rollback` возвращает подтверждённую конфигурацию; POST `/api/hardware/recovery` включает восстановление. Оба требуют текущие `token` и `generation`.

В восстановлении UART-консоль использует подтверждённую распиновку, если она не пересекается с моторными GPIO подтверждённой и пробной карт. При пересечении UART отключается; используйте native USB или сеть. LED/RGB в восстановлении отключены. При работающей точке доступа доступен также командный UDP **4535**. Разрешены чтение состояния, памяти, журнала и причин перезапуска, настройка сети и аппаратной конфигурации. Управление двигателями заблокировано. Неудачный аппаратный вариант автоматически не запускается повторно. Если сохранённая конфигурация использовала Bluetooth, отсутствующий в новой сборке, параметры привода сохраняются: выполните `/api/hardware/rollback`, чтобы начать пробный запуск прежнего оборудования с выключенным Bluetooth, затем проверьте и подтвердите конфигурацию.

## Обновление по сети

Прочитайте GET `/api/ota`, затем передайте POST `/api/ota/arduino token=…` с токеном из ответа. Повторный GET `/api/ota` показывает имя устройства и временный пароль ArduinoOTA. Используйте их для [обновления ArduinoOTA](ota.md). Окно загрузки ограничено десятью минутами.

В начале обновления выходы останавливаются, дальнейшее движение блокируется до перезапуска, в том числе после ошибки загрузки. OTA требует подходящих разделов flash; причина недоступности указана в `/api/ota`. Первичная запись прошивки и таблицы разделов выполняется через USB.

## Формат внешнего протокола

По UART/USB и TCP запрос — ASCII-строка с префиксом `@` и окончанием CR, LF или CRLF. По UDP тот же запрос передаётся одной датаграммой без окончания строки. Данные кодируются как `application/x-www-form-urlencoded`, включая UTF-8. Максимум — **1024 байта**, без окончания строки; ключ — до 32 байт, значение после декодирования — до 128 байт. Повторяющиеся ключи и управляющие символы отклоняются.

Открытие сессии:

```text
@v=1&cid=1&method=GET&path=%2Fapi%2Fhello&client=12345
```

`client` — случайное ненулевое число uint32, выбранное клиентом. Ответ JSON содержит `boot` (16 шестнадцатеричных цифр), `sid` и `selection`. Последующие запросы включают их и возрастающий ненулевой `cid`:

```text
@v=1&cid=2&boot=0123456789abcdef&sid=123&selection=1&method=GET&path=%2Fapi%2Fstatus&page=0
```

`boot` и `sid` берите из ответа своего устройства. `selection` защищает команды HUD от исполнения после смены выбранной поворотки. Поля `v`, `cid`, `boot`, `sid`, `selection`, `method`, `path`, `page` зарезервированы протоколом; остальные поля передаются операции API. Параметр `offset` каталога HUD остаётся обычным параметром API.

Ответ ограничен **1200 байтами** и содержит `status`, `type`, `offset`, `next`, `total`, `revision` и `base64`: до 672 байт исходного тела ответа, закодированных Base64. Для следующей страницы выполните новый GET с новым `cid` и `page=next`. `next=null` означает конец; `revision` и `total` должны совпадать у всех страниц. После сборки декодируйте тело согласно `type`. Ошибки самого протокола возвращаются непосредственно в поле `error`.

Коды: 200 — успех, 202 — ожидается результат HUD, 400 — неверные параметры, 403 — операция недоступна, 409 — конфликт состояния/сессии, 503 — операция временно недоступна или ошибка сохранения.

Поддерживаются четыре сессии. Сессия привязана к интерфейсу и отправителю; для UDP сохраняйте один исходный порт, для TCP — одно соединение. Выполняйте один запрос за раз. Идентичный повтор последнего запроса получает сохранённый ответ без повторного исполнения; старые номера и тот же номер с другим содержимым отклоняются. При вытеснении сессии или перезапуске старые запросы не исполняются. После потери ответа повторяйте **точно тот же запрос**; после утраты сессии сначала проверяйте состояние устройства.
